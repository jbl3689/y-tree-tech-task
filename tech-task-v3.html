Product brief · Take-home

Connect your accounts

A new client is joining. Before we can advise them, we need a recent statement from every provider they hold money with. This is the screen where they get that done.

Full-stack ⏱ ~2 hours 🤖 AI allowed

Background

Why this matters

New clients hold money across several providers — banks, pensions, investment platforms. We can't give advice until we have a recent statement from each one.

Onboarding stalls here more than anywhere else. The client has to remember who they're with, chase down statements, and know when they're finally done. This screen is where that happens, so it needs to make the whole thing feel obvious.

What the client can do

The interactions

  • See their providers and, for each, whether we already have a good statement.
  • Add providers they hold — searching a list of known providers and picking several at once.
  • Remove a provider they added by mistake or no longer hold.
  • Upload a statement for a provider.
  • Filter the list by status to see what still needs attention.
  • Submit once everything is in order.

Two lists are involved, and they behave differently:

Known providers

The full set of providers a client could hold — the list they search and pick from when adding.

→
The client's accounts

The providers this client has actually added, each with its own statement status. This is the on-screen list.

The rules

How it should behave

A provider is always in one of three states

  • Missing — we have no statement.
  • Uploaded — we have a recent statement.
  • Outdated — we have a statement, but it is more than 3 months old, so it no longer counts.

And these must always hold

  • A provider the client has already added should not appear again when they go to add more.
  • The client can submit only when every provider has a current statement — nothing Missing or Outdated.
  • An incomplete set must never be accepted, even if the client finds a way around the screen. The client should be told clearly what's still wrong.
  • At every step the client knows what's happening — what's loading, what failed, and what succeeded.

The heart of it

“Am I ready to submit?” is the question the whole screen answers. Everything the client does — adding, removing, uploading — should move them visibly closer to, or further from, being able to submit.

Boundaries

Out of scope

  • No real file handling — treat an upload as just a file name and a date.
  • No sign-in and no multiple clients — assume one client, with a few providers already added to start from.
  • No production concerns (deployment, scaling, real provider data).

Logistics

How to approach it

  • It's a full-stack task. Build the screen and the service behind it — roughly half and half. How you shape the API, where logic lives, and how the two talk is entirely your design.
  • Set the project up yourself — no starter repo. This is a brief, not a scaffold: you begin from scratch and stand the project up. Use React + TypeScript on the front end; the rest of the front-end tooling is your call. On the back end use Kotlin/Java (Spring Boot). We expect you to be comfortable with basic project setup.
  • Set up your own tests and seed data. Nothing is wired up for you — add a test runner where you need one, and prepare your own seed or mock data to work against. Include a few meaningful tests — at least one on each side — covering the behaviour you'd most want to protect. An e2e test (e.g. Playwright) exercising the submit flow is a plus, not required.
  • ~2 hours. Using AI is fine and encouraged; we care about the result and that you understand it.
  • Add a short NOTES.md — key decisions, trade-offs, and what you'd do with more time.

Afterwards we'll sit down and read through the code together.
